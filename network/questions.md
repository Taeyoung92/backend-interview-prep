# 네트워크

---

## 브라우저 요청 시 처리 흐름
사용자가 URL을 입력하면 DNS에서 IP를 조회하고 서버에 TCP 연결을 맺습니다. 브라우저가 HTTP 요청을 보내면, 저희 서비스 기준으로는 Route 53에서 도메인을 라우팅하고 ALB가 요청을 받아 해당 EC2로 전달합니다. Spring Controller가 요청을 받아 Service → Repository 순으로 처리하고 DB에서 데이터를 조회해 JSON으로 응답합니다. 프론트엔드는 응답받은 데이터로 화면을 렌더링합니다.

---

## TCP/UDP의 정의/차이점/장단점
TCP(Transmission Control Protocol) - 연결을 먼저 맺고(connection), 데이터가 정확하고 순서대로 도착하는 것을 보장하는 신뢰성 중심 프로토콜.
UDP(User Datagram Protocol) - 연결 과정 없이, 데이터를 일단 빠르게 던지는 속도 중심 프로토콜. 도착 여부/순서를 보장하지 않음.

**차이점**

| 구분 | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결형 (handshake 필요) | 비연결형 (그냥 전송) |
| 신뢰성 | 보장 (재전송으로 손실 복구) | 보장 안 함 (손실돼도 끝) |
| 순서 보장 | 보장 (순서대로 재조립) | 보장 안 함 |
| 속도 | 상대적으로 느림 | 빠름 |
| 흐름·혼잡 제어 | 있음 | 없음 |
| 헤더 크기 | 큼 (20~60 byte) | 작음 (8 byte) |
| 전송 단위 | 바이트 스트림 | 데이터그램(패킷) |

**장단점**

TCP
- 장점 : 데이터가 빠짐없이, 순서대로 도착함. 손실되면 재전송하고, 네트워크 혼잡 시 속도를 조절(흐름·혼잡 제어). 신뢰성이 생명인 통신에 적합
- 단점 : 연결 수립·확인·제어 과정 때문에 상대적으로 느리고 오버헤드가 큼

UDP
- 장점 : 연결·확인 절차가 없어 빠르고 가벼움. 실시간성이 중요한 통신에 적합. 1:다 전송(브로드캐스트·멀티캐스트)도 가능
- 단점 : 데이터가 유실·중복·순서 뒤바뀜이 생길 수 있고, 이를 막으려면 애플리케이션이 직접 처리해야 함

TCP와 UDP를 사용하는 경우
- TCP - 한 글자라도 틀리면 안되는 것 > 웹, 이메일 ,파일전송 >> 데이터가 깨지면 안 됨
- UDP - 조금 손실돼도 되지만 빨라야 하는 것 > 실시간 스트리밍, 화상통화/음성통화, 온라인 게임, DNS 조회

## HTTP란?
HTTP(HyperText Transfer Protocol) = 웹에서 브라우저와 서버가 데이터를 주고받는 통신 규약.

1. Stateless(무상태) - 서버는 이전 요청을 기억하지 못함. 요청 하나하나를 매번 처음 보는 손님처럼 독립적으로 처리함
2. Connectionless(비연결성) - 요청<>응답이 끝나면 연결을 끊음.

---

## 쿠키(Cookie)란?
쿠키 = 서버가 만들어서 브라우저(클라이언트)에 저장해두는 작은 데이터 조각.

동작 흐름 :
1. 브라우저 > 서버 : 요청
2. 서버 > 브라우저 : 응답 + 쿠키 저장(Set-Cookie)
3. 브라우저 : 쿠키를 자기 쪽에 저장
4. 이후 모든 요청마다 > 서버 : 저장한 쿠키를 자동으로 같이 보냄
5. 서버 : 쿠키를 보고 사용자 인식

*** 저장 위치가 클라이언트(브라우저). 그래서 사용자가 열어보거나 수정이 가능해 보안에 취약함

사용사례 : 덜 민감하고, 클라이언트가 들고 있어도 되는 것
- 자동 로그인, 아이디 저장, 오늘 하루 팝업 보지 않기, 장바구니(비 로그인상태), 사용자 언어/테마 설정 등

---

## 세션(Session)이란?
세션 = 중요한 정보는 서버가 보관하고, 브라우저에는 식별표(Session ID)만 쿠키로 주는 방식.

동작 흐름 :
1. 브라우저 > 서버 : 로그인
2. 서버 : 사용자 정보를 서버 메모리/DB에 저장 + 세션 ID 발급
3. 서버 > 브라우저 : 세션 ID만 쿠키로 전달
4. 브라우저 : 세션 ID(쿠키)만 저장
5. 이후 요청마다 > 서버 : 세션 ID 전송
6. 서버 : 세션 ID로 서버에 보관된 진짜 정보를 찾아 사용자 인식

*** 실제 정보는 서버에 있고, 브라우저엔 식별표만 있음. 그래서 쿠키보다 안전함 > 세션도 세션 ID를 전달할 때 쿠키를 사용함. 즉 세션은 쿠키를 안전하게 쓰는 방식에 가까움.

사용 사례 : 민감하고, 서버가 통제해야 하는 것
- 로그인 인증 상태, 장바구니(로그인 상태), 결제 진행 정보 등

## 웹소켓이란?
웹소켓(WebSocket) = 한 번 연결하면, 그 연결을 계속 유지하면서 서버와 클라이언트가 양방향으로 자유롭게 데이터를 주고받는 통신 프로토콜.

핵심 특징 :
- 양방향 : 서버도 클라이언트도 먼저 말을 걸 수 있음
- 연결 지속 : 한 번 연결하면 끊지 않고 계속 사용(HTTP처럼 매번 끊지 않음)
- 가벼움 : 연결 후엔 매번 무거운 HTTP 헤더를 붙이지 않아 오버헤드가 적음

연결 방법 :
- 연결의 시작은 HTTP로 함.(Handshake)
- 처음엔 HTTP로 핸드셰이크 > 101 Switching Protocols 응답으로 프로토콜이 웹소켓으로 바뀜
- 이후엔 같은 TCP 연결을 그대로 쓰되 웹소켓 프로토콜로 통신
- 주소 체계가 http:// → ws://, https:// → wss://(암호화) 로 바뀜

*** HTTP로 시작하는 이유? : 기존 웹 인프라(포트 80/443, 방화벽, 프록시)와 호환을 위해서. 새 포트를 열지 않고 기존 HTTP 통로로 자연스럽게 연결을 시작.

## 실시간 통신 방식 4가지

1. **Polling(폴링)** - 클라이언트가 일정 주기로 계속 신규 요청
   - 단점 : 새 데이터가 없어도 계속 요청 → 불필요한 트래픽 및 서버 부하. 주기 사이에 지연도 생김

2. **Long Polling(롱 폴링)** - 요청을 보내면 서버가 데이터가 생길때까지 응답을 미룸. 응답 오면 즉시 다시 요청
   - 폴링보다 낫지만, 응답 때마다 연결을 다시 맺어야함

3. **SSE(Server-Sent Events)** - 연결을 유지하되 서버 → 클라이언트 단방향으로만 데이터를 밀어줌
   - 알림/시세처럼 받기만 하면 되는 경우 가볍고 충분함. 단, 클라이언트가 보낼 길은 없음

4. **WebSocket(웹소켓)** - 연결 유지 + 양방향. 서로 자유롭게 송수신

## 알림을 구현할 때 어떤 구현 방법이 있는지
방법 3가지 - Polling / SSE / WebSocket

**1. 폴링**
- 장점 : 구현이 가장 단순. 특별한 인프라 불필요. HTTP 그대로 사용
- 단점 : 새 알림이 없어도 계속 요청 → 트래픽/서버 부하 낭비. 주기 사이의 지연 발생
- 적합 : 실시간성이 별로 중요하지 않고, 트래픽이 적은 간단한 서비스

**2. SSE**
- 장점 : 알림에 가장 적합한 구조(알림은 서버가 일방적으로 주는 단방향이므로). 웹소켓보다 가볍고 구현이 간단함. HTTP 기반이라 자동 재연결 등 지원
- 단점 : 단방향이라 클라이언트가 서버로 보낼 길은 없음. 브라우저당 연결 수 제한, 일부 구형 환경 지원 이슈
- 적합 : 실시간 알림, 피드 업데이트처럼 받기만 하면 되는 경우

**3. 웹소켓**
- 장점 : 실시간성 최고, 양방향이라 알림 + 채팅 등 복합 기능에 유리
- 단점 : 양방향 연결 유지에 서버 자원 부담이 큼. 구현·운영 복잡도 높음 (알림만 필요하면 과한 선택)
- 적합 : 채팅처럼 양방향이 함께 필요하거나, 매우 높은 실시간성이 요구될 때

**고려해야 할 포인트**
1. 알림 저장(영속성) - 사용자가 접속 중이 아닐 때 온 알림은? → DB에 저장해두고, 접속하면 보여주기. 실시간 전송과 별개로 저장은 필수.
2. 읽음 처리 - 읽음/안읽음 상태 관리, 안읽은 개수 표시(배지).
3. 다중 서버 환경 - 서버가 여러 대면, 알림 대상 사용자가 어느 서버에 연결돼 있는지 모름 → Redis Pub/Sub이나 메시지 큐(Kafka)로 서버 간에 알림을 전파.
4. 연결 관리 - SSE/웹소켓은 연결이 끊길 수 있음 → 재연결 처리, 끊긴 연결 정리(좀비 커넥션 방지)
5. 비동기 처리 - 알림 전송이 본 로직(예 : 주문 처리)을 막으면 안 됨 → 비동기/이벤트 기반으로 분리. 스프링이면 @Async나 이벤트 발행(ApplicationEventPublisher).
6. 장애 대응 - 알림 전송 실패 시 재시도, 푸시 서비스 장애 시 처리.
