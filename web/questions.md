## 브라우저에서 서버로 요청 시 처리 흐름을 설명해보세요

### 한 줄 요약 (ver1)
사용자가 URL을 입력하면 DNS에서 IP를 조회하고 서버에 TCP 연결을 맺습니다. 브라우저가 HTTP 요청을 보내면, 저희 서비스 기준으로는 Route 53에서 도메인을 라우팅하고 ALB가 요청을 받아 해당 EC2로 전달합니다. Spring Controller가 요청을 받아 Service → Repository 순으로 처리하고 DB에서 데이터를 조회해 JSON으로 응답합니다. 프론트엔드는 응답받은 데이터로 화면을 렌더링합니다.

### 상세 설명 (ver2)

#### 1. 브라우저 > 서버(네트워크 구간)
브라우저가 URL의 도메인을 DNS로 IP조회
해당 IP/포트로 TCP 연결(3-way handshake), HTTPS면 TLS 핸드셰이크 추가
브라우저가 http 요청 메시지 전송(Method, URL, Header, Body)

*3-way handshake(TCP 연결 수립) :
TCP는 데이터를 주고받기 전에 **양쪽이 서로 통신할 준비가 됐는지 확인**합니다. 이때 패킷을 3번 주고받기 때문에 3-way handshake라고 함
```
클라이언트                         서버
│  ──── ① SYN ────────────→    │   "연결할게" (요청)
│                              │
│  ←─── ② SYN + ACK ───────    │   "좋아, 나도 준비됨" (수락+응답)
│                              │
│  ──── ③ ACK ─────────────→   │   "확인했어, 시작하자"
│                              │
└──── 이제 데이터 송수신 가능 ────┘
```
>> 데이터를 보내기 전에 양쪽 모두 "보낼 준비 + 받을 준비"가 됐음을 확인하는 절차

*TLS handshake (암호화 통신 준비) :
3-way handshake로 TCP 연결이 맺어지면, **HTTPS의 경우** 그 위에서 한 단계가 더 진행됨. 주고받는 데이터를 암호화하기 위해 "어떻게 암호화할지 합의하고, 암호화 키를 안전하게 교환"하는 절차가 TLS handshake
암호화 방식 합의 - 클라이언트와 서버가 서로 지원하는 암호화 알고리즘(Cipher Suite) 중 공통으로 쓸 것을 정함
서버 인증 -  서버가 **SSL/TLS 인증서**를 제시하고, 클라이언트는 이 인증서가 신뢰할 만한 기관(CA)이 발급한 진짜인지 검증 (→ 접속한 서버가 사칭이 아닌지 확인)
세션 키 교환 - 이후 실제 데이터를 암호화할 대칭키(세션 키)를 안전하게 공유

#### 2. WAS 진입(Servlet Container)
요청이 톰캣 같은 WAS(Servlet Container)에 도착
톰캣은 매 요청마다 스레드를 만들지 않고 Thread Pool에서 스레드 하나를 꺼내 할당(커넥션 폭주 방지/재사용)
요청/응답 정보를 담은 HttpServletRequest / HttpServletResponse 객체를 생성

#### 3. Spring MVC 내부 (핵심)
DispatcherServlet이 요청을 받음
HandlerMapping에게 해당 URL 처리 컨트롤러 요청하여 Handler(Controller 메서드) 응답받음
HandlerAdapter를 통해 해당 컨트롤러 메서드를 실제로 호출
호출 전후로 Interceptor(인증/로깅 등)가 동작할 수 있음
컨트롤러가 Service > Repository 순으로 비즈니스 로직 수행

#### 4. DB 접근(Connection Pool)
Repository가 DB 작업이 필요하면 Connection Pool(예시 : HikariCP)에서 미리 만들어둔 DB 커넥션을 빌려옴
쿼리 실행 후 커넥션을 **닫지 않고 풀에 반납** (커넥션 생성 비용이 크기 때문에 재사용)
결과를 Service → Controller로 반환

#### 5. 응답 생성(View 렌더링)
화면(View) 반환의 경우(JSP/Themeleaf 등) - 컨트롤러가 논리적 View 이름을 반환 > ViewResolver가 이를 실제 경로로 변환 > **JSP**가 Model 데이터를 받아 **HTML로 렌더링** (JSP는 내부적으로 서블릿으로 변환·컴파일되어 실행됨)

데이터(JSON) 반환의 경우(REST API) - 메서드에 @ResponseBody (또는 @RestController)가 있으면 ViewResolver를 거치지 않음 > **HttpMessageConverter**가 객체를 JSON으로 직렬화

#### 6. 응답 > 브라우저
DispatcherServlet이 최종 응답을 HttpServletResponse에 담음
톰캣이 HTTP 응답 메시지로 만들어 브라우저에 전송
사용한 스레드는 Thread pool에 반납
브라우저가 HTML/JSON을 파싱해 화면에 렌더링

## HTTP란?
HTTP(HyperText Transfer Protocol) = 웹에서 브라우저와 서버가 데이터를 주고받는 통신 규약.

1. Stateless(무상태) - 서버는 이전 요청을 기억하지 못함. 요청 하나하나를 매번 처음 보는 손님처럼 독립적으로 처리함
2. Connectionless(비연결성) - 요청<>응답이 끝나면 연결을 끊음.

---

## 쿠키(Cookie)란?
쿠키 = 서버가 만들어서 브라우저(클라이언트)에 저장해두는 작은 데이터 조각.

동작 흐름 :
1. 브라우저 > 서버 : 요청
2. 서버 > 브라우저 : 응답 + 쿠키 저장(Set-Cookie)
3. 브라우저 : 쿠키를 자기 쪽에 저장
4. 이후 모든 요청마다 > 서버 : 저장한 쿠키를 자동으로 같이 보냄
5. 서버 : 쿠키를 보고 사용자 인식

*** 저장 위치가 클라이언트(브라우저). 그래서 사용자가 열어보거나 수정이 가능해 보안에 취약함

사용사례 : 덜 민감하고, 클라이언트가 들고 있어도 되는 것
- 자동 로그인, 아이디 저장, 오늘 하루 팝업 보지 않기, 장바구니(비 로그인상태), 사용자 언어/테마 설정 등

---

## 세션(Session)이란?
세션 = 중요한 정보는 서버가 보관하고, 브라우저에는 식별표(Session ID)만 쿠키로 주는 방식.

동작 흐름 :
1. 브라우저 > 서버 : 로그인
2. 서버 : 사용자 정보를 서버 메모리/DB에 저장 + 세션 ID 발급
3. 서버 > 브라우저 : 세션 ID만 쿠키로 전달
4. 브라우저 : 세션 ID(쿠키)만 저장
5. 이후 요청마다 > 서버 : 세션 ID 전송
6. 서버 : 세션 ID로 서버에 보관된 진짜 정보를 찾아 사용자 인식

*** 실제 정보는 서버에 있고, 브라우저엔 식별표만 있음. 그래서 쿠키보다 안전함 > 세션도 세션 ID를 전달할 때 쿠키를 사용함. 즉 세션은 쿠키를 안전하게 쓰는 방식에 가까움.

사용 사례 : 민감하고, 서버가 통제해야 하는 것
- 로그인 인증 상태, 장바구니(로그인 상태), 결제 진행 정보 등

---

## 쿠키와 세션의 차이?

| 구분 | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | 클라이언트(브라우저) | 서버 |
| 보안 | 낮음(클라이언트가 열람·수정 가능) | 높음(서버가 통제) |
| 생명주기 | 만료일 설정 가능, 브라우저 종료 후에도 유지 가능 | 브라우저 종료 또는 서버 삭제 시 만료 |
| 서버 부담 | 없음(클라이언트가 보관) | 있음(서버 메모리/DB에 저장) |
| 용도 | 비민감 정보(자동 로그인, 설정 등) | 민감 정보(로그인 인증 상태 등) |

>> 세션은 쿠키를 없애는 게 아니라, 쿠키에는 식별표(Session ID)만 두고 실제 정보는 서버에서 관리하는 방식. 즉 세션은 쿠키를 안전하게 활용하는 패턴.

---

## 세션을 쓰는데 서버가 여러 대면?
세션은 특정 서버 메모리에 저장됨. 사용자가 서버 1에서 로그인했는데 다음 요청이 서버 2로 가면, 서버 2엔 세션이 없어 로그아웃됨. 해결책:
- **Sticky Session** : 같은 사용자는 늘 같은 서버로 (그 서버 죽으면 세션 날아감)
- **세션 클러스터링** : 서버끼리 세션 복제 (서버 늘면 부담이 올라감)
- **외부 세션 저장소(Redis)** : 세션을 Redis에 모아두고 모든 서버가 공유 → 가장 많이 사용하는 방법

## JWT vs 세션
JWT는 토큰 자체에 정보를 담아 서버가 상태를 저장하지 않음(Stateless).

| 구분 | 세션 | JWT |
|---|---|---|
| 상태 저장 | 서버에 저장 | 토큰 자체에 포함 |
| 서버 확장 | 다중 서버 시 공유 필요 | Stateless라 쉬움 |
| 강제 만료 | 서버에서 즉시 삭제 가능 | 만료 전까진 유효 |

- 장점 : 서버에 세션 저장 불필요 → 서버 확장 쉬움, 다중 서버에 유리
- 단점 : 토큰을 서버가 강제로 만료시키기 어려움. 한 번 발급하면 만료 전까지 유효
- 토큰 탈취 시 : 만료 전까진 악용 가능 → 짧은 수명의 Access Token + 긴 Refresh Token 조합, 탈취 의심 시 Refresh Token 무효화

## HTTPS는 왜 대칭키/비대칭키를 둘 다 쓰나?
- **비대칭키(공개키/개인키)** : 안전하지만 느림 → 키 교환/인증에만 사용
- **대칭키(하나의 키)** : 빠르지만 키 공유가 위험 → 실제 데이터 암호화에 사용

비대칭키로 안전하게 대칭키를 공유한 뒤, 이후 통신은 빠른 대칭키로 암호화함. 두 방식의 장점만 조합한 것.
