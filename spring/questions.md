# Spring / Spring Boot

---

## 싱글톤과 스프링

### 스프링은 왜 Singleton 패턴을 사용할까?
> 성능과 자원 효율때문에.

웹 애플리케이션은 초당 수십~수백 개의 요청이 들어옴. 만약 요청마다 컨트롤러/서비스/리포지토리 객체를 매번 새로 생성하면 객체 생성 비용이 계속 발생하고(메모리 및 CPU 낭비) GC가 처리할 객체가 폭증하여 성능 저하로 이어짐. 그래서 스프링은 각 Bean을 딱 하나만 만들어 컨테이너에 보관하고, 모든 요청이 그 하나를 공유함. 객체를 하나만 만들어서 재사용하니 메모리와 생성 비용이 크게 절약됨.

---

### 스프링 싱글톤 vs 일반 싱글톤 패턴
둘 다 '객체 하나만' 이라는 결과는 같지만, 방식과 범위가 다름

일반 싱글톤 패턴 - 클래스 안에 private 생성자 + static 인스턴스를 직접 구현
JVM(클래스로더) 단위로 유일 > 한 JVM 안에서 진짜 단 하나

스프링 싱글톤 - 개발자가 코드를 직접 짤 필요가 없음. 스프링 컨테이너가 객체를 하나만 만들어 관리
컨테이너 단위로 유일 > JVM 안이 아닌 컨테이너당 하나

>> 일반 싱글톤은 클래스 자체가 싱글톤을 강제하지만, 스프링 싱글톤은 평범한 객체를 컨테이너가 싱글톤으로 관리할 뿐임

---

### IoC 컨테이너와 싱글톤의 관계
IoC 컨테이너 : Bean을 생성/보관/관리하는 주체.
- IoC(제어의 역전, Inversion of Control) : 객체의 생성/생명주기 관리를 개발자가 아니라 컨테이너가 대신 맡는것
- 스프링은 이 컨테이너가 Bean을 만들 때 기본적으로 싱글톤으로 만들어 내부저장소에 보관

---

### 싱글톤 설계 시 주의점
무상태(Stateless)로 설계해야한다.
> 하나의 객체를 여러 요청(여러 스레드)이 동시에 공유하기 때문에, 객체가 상태를 가지면 동시성 문제가 터짐.

주의점 : 공유 필드에 특정 요청/클라이언트의 데이터를 저장하지 말것. 값은 지역변수, 파라미터, 반환값으로 처리(스레드마다 독립적)할것. 읽기 전용 데이터나 공유 가능한 것만 필드로 생성할것.

---

### IoC/DI가 싱글톤 문제를 어떻게 해결하는가
일반 싱글톤 패턴은 여러 단점이 존재함.
- getInstance()로 직접 호출 > 코드가 특정 클래스에 강하게 결합됨
- private 생성자라 상속/확장이 어려움
- 구체 클래스에 의존 > 테스트 시 가짜 객체(Mock)로 교체 불가 > 테스트 어려움
- 전역 상태라 객체 지향(유연성)을 해침

이때 DI(의존성 주입, **Dependency Injection**)가 이것을 해결

- 객체를 직접 가져오지(getInstance)않고 주입받으니, 구체 클래스에 의존하지 않음 > 인터페이스에 의존 가능
- 테스트할 땐 가짜 구현을 주입하면 됨 > 테스트가 쉬워짐
- 코드에 싱글톤 관련 흔적(private 생성자 등)이 전혀 없음

---

### 스프링이 싱글톤의 단점을 보완한 방법

| 일반 싱글톤 단점 | 스프링 보완 |
|---|---|
| 코드 오염(private 생성자, static) | 평범한 POJO를 컨테이너가 관리 → 코드 깔끔 |
| 구체 클래스 의존 → 결합도↑ | **DI**로 인터페이스에 의존 가능 |
| 테스트 어려움 | **DI**로 Mock 주입 → 테스트 용이 |
| 상속·확장 어려움 | 일반 객체라 자유로움 |
| 상태 공유 시 동시성 문제 | (이건 보완이 아니라) **무상태 설계로 회피** |
| 항상 하나여야만 함(유연성↓) | **Scope** 지정으로 필요 시 prototype, request 등 선택 가능 |

>>> 웹은 요청이 많아 객체를 매번 만들면 비효율적이라, 스프링은 Bean을 싱글톤으로 관리해 재사용함. 일반 싱글톤 패턴은 코드 오염·테스트 곤란·결합도 증가 같은 단점이 있는데, 스프링은 IoC 컨테이너가 객체 생성·관리를 대신하고 DI로 주입해주어 이 단점들을 없앰. 다만 객체를 공유하므로 동시성 문제를 피하려면 무상태로 설계해야 하고, 싱글톤이 부적합한 경우엔 스코프를 바꿔 대응할 수 있음.

## Bean 이란?
스프링 컨테이너가 만들고 관리하는 객체.
> 특별한 종류의 객체가 아닌, 스프링이 직접 생성/관리하는 자바 객체

```java
@Service          // ← "이 객체를 Bean으로 관리해줘"라고 표시
public class OrderService {
    public void order() { ... }
}
```

내가 `new OrderService()`로 직접 만든 객체는 **Bean이 아닙니다.** (내가 만들고 내가 관리)
`@Service`, `@Controller`, `@Repository`, `@Component` 같은 표시를 붙이거나 `@Bean`으로 등록하면, **스프링이 대신 만들어 관리** → 이게 Bean입니다.

핵심 구분: **누가 만들고 관리하느냐.** 내가 `new`로 만들면 일반 객체, **스프링이 만들어 관리하면 Bean.**

---

## 컨테이너란?
Bean을 만들고, 보관하고, 관리하고, 연결해주는 공간
스프링이 애플리케이션을 시작할 때 만드는 거대한 객체 보관소. 정식 명칭은 ApplicationContext

컨테이너가 하는 일:
- 생성 - @Service 등이 붙은 클래스를 찾아 객체를 만듦
- 보관 - 만든 Bean을 내부 저장소에 담아둠
- 연결(DI) - Bean끼리 필요한 의존관계를 자동으로 주입
- 관리 - Bean의 생성부터 소멸까지 생명주기를 책임짐

---

## 스레드 풀과 커넥션 풀의 관계 (스레드 100, 커넥션 10이면?)
스레드 풀(톰캣)은 요청을 처리하는 일꾼, 커넥션 풀(HikariCP)은 DB와 대화할 권한. 별개의 자원.

스레드 100인데 커넥션 10이면 : 100개의 요청이 동시에 들어와도 DB 작업은 10개만 가능. 나머지 90개 스레드는 커넥션을 기다리며 블로킹됨. 대기가 길어지면 `connectionTimeout`으로 예외 발생.

---

## @Transactional은 어떻게 동작하나?
스프링이 AOP(프록시)로 메서드를 감쌈. 메서드 호출 시 프록시가 가로채서

① 메서드 시작 전 → 트랜잭션 시작 (커넥션 획득, autocommit off)
② 메서드 실행 (비즈니스 로직)
③ 정상 종료 → commit
④ 런타임 예외 발생 → rollback

---

## 싱글톤 Bean인데 어떻게 동시 처리되나? 동시성 문제는 왜 안 생기나?
객체는 하나지만 스레드는 여러 개(톰캣 스레드 풀). 여러 스레드가 같은 Bean의 메서드를 동시에 실행함.

동시성 문제가 안 생기는 이유 : 메서드 안의 지역변수/매개변수는 각 스레드의 Stack에 따로 저장되기 때문. 무상태(공유 필드에 상태를 안 둠)로 설계하면 안전함. 반대로 공유 필드에 요청별 데이터를 저장하면 스레드끼리 값이 덮어써져 문제가 발생함.

---

## 생성자 주입을 권장하는 이유
- `final` 사용 가능 → 불변성 보장, 주입 누락을 컴파일 시점에 발견
- 순환 참조를 앱 시작 시점에 감지 (필드 주입은 런타임에야 터짐)
- 테스트 쉬움 → 스프링 없이도 `new`로 의존성 주입 가능
- 의존성이 명시적으로 드러남

## AOP란?
AOP(Aspect-Oriented Programming, 관점 지향 프로그래밍) = 여러 곳에 공통으로 끼어드는 부가 기능을 핵심 로직에서 떼어내 한 곳에서 관리하는 방식.

```java
// AOP 없이 — 모든 메서드에 같은 코드가 반복됨
public void order() {
    트랜잭션_시작();
    try {
        // 진짜 하고 싶은 일 (주문 로직)
        트랜잭션_커밋();
    } catch (e) {
        트랜잭션_롤백();
    }
}
public void payment() {
    트랜잭션_시작(); // 또 반복...
    ...
}
```

이 반복되는 부가 기능(트랜잭션 등)을 한 곳에 모아 정의해두고, 스프링이 메서드 실행 시 자동으로 끼워 넣어주는 게 AOP.

```java
// AOP 사용 — 핵심 로직만 남고, 트랜잭션은 어노테이션 하나로
@Transactional
public void order() {
    // 진짜 하고 싶은 일만 작성 (트랜잭션 코드 없음)
}
```
