## 브라우저에서 서버로 요청시 처리 흐름

### 1. 브라우저 > 서버(네트워크 구간)
브라우저가 URL의 도메인을 DNS로 IP조회
해당 IP/포트로 TCP 연결(3-way handshake), HTTPS면 TLS 핸드셰이크 추가
브라우저가 http 요청 메시지 전송(Method, URL, Header, Body)

*3-way handshake(TCP 연결 수립) :
TCP는 데이터를 주고받기 전에 **양쪽이 서로 통신할 준비가 됐는지 확인**합니다. 이때 패킷을 3번 주고받기 때문에 3-way handshake라고 함
```
클라이언트                         서버
│  ──── ① SYN ────────────→    │   "연결할게" (요청)
│                              │
│  ←─── ② SYN + ACK ───────    │   "좋아, 나도 준비됨" (수락+응답)
│                              │
│  ──── ③ ACK ─────────────→   │   "확인했어, 시작하자"
│                              │
└──── 이제 데이터 송수신 가능 ────┘
```
>> 데이터를 보내기 전에 양쪽 모두 "보낼 준비 + 받을 준비"가 됐음을 확인하는 절차

*TLS handshake (암호화 통신 준비) :
3-way handshake로 TCP 연결이 맺어지면, **HTTPS의 경우** 그 위에서 한 단계가 더 진행됨. 주고받는 데이터를 암호화하기 위해 "어떻게 암호화할지 합의하고, 암호화 키를 안전하게 교환"하는 절차가 TLS handshake
암호화 방식 합의 - 클라이언트와 서버가 서로 지원하는 암호화 알고리즘(Cipher Suite) 중 공통으로 쓸 것을 정함
서버 인증 -  서버가 **SSL/TLS 인증서**를 제시하고, 클라이언트는 이 인증서가 신뢰할 만한 기관(CA)이 발급한 진짜인지 검증 (→ 접속한 서버가 사칭이 아닌지 확인)
세션 키 교환 - 이후 실제 데이터를 암호화할 대칭키(세션 키)를 안전하게 공유

### 2. WAS 진입(Servlet Container)
요청이 톰캣 같은 WAS(Servlet Container)에 도착
톰캣은 매 요청마다 스레드를 만들지 않고 Thread Pool에서 스레드 하나를 꺼내 할당(커넥션 폭주 방지/재사용)
요청/응답 정보를 담은 HttpServletRequest / HttpServletResponse 객체를 생성

### 3. Spring MVC 내부 (핵심)
DispatcherServlet이 요청을 받음
HandlerMapping에게 해당 URL 처리 컨트롤러 요청하여 Handler(Controller 메서드) 응답받음
HandlerAdapter를 통해 해당 컨트롤러 메서드를 실제로 호출
호출 전후로 Interceptor(인증/로깅 등)가 동작할 수 있음
컨트롤러가 Service > Repository 순으로 비즈니스 로직 수행

### 4. DB 접근(Connection Pool)
Repository가 DB 작업이 필요하면 Connection Pool(예시 : HikariCP)에서 미리 만들어둔 DB 커넥션을 빌려옴
쿼리 실행 후 커넥션을 **닫지 않고 풀에 반납** (커넥션 생성 비용이 크기 때문에 재사용)
결과를 Service → Controller로 반환

### 5. 응답 생성(View 렌더링)
화면(View) 반환의 경우(JSP/Themeleaf 등) - 컨트롤러가 논리적 View 이름을 반환 > ViewResolver가 이를 실제 경로로 변환 > **JSP**가 Model 데이터를 받아 **HTML로 렌더링** (JSP는 내부적으로 서블릿으로 변환·컴파일되어 실행됨)

데이터(JSON) 반환의 경우(REST API) - 메서드에 @ResponseBody (또는 @RestController)가 있으면 ViewResolver를 거치지 않음 > **HttpMessageConverter**가 객체를 JSON으로 직렬화

### 6. 응답 > 브라우저
DispatcherServlet이 최종 응답을 HttpServletResponse에 담음
톰캣이 HTTP 응답 메시지로 만들어 브라우저에 전송
사용한 스레드는 Thread pool에 반납
브라우저가 HTML/JSON을 파싱해 화면에 렌더링

## 스프링은 왜 Singleton 패턴을 사용할까?
> 성능과 자원 효율때문에.

웹 애플리케이션은 초당 수십~수백 개의 요청이 들어옴. 만약 요청마다 컨트롤러/서비스/리포지토리 객체를 매번 새로 생성하면 객체 생성 비용이 계속 발생하고(메모리 및 CPU 낭비) GC가 처리할 객체가 폭증하여 성능 저하로 이어짐. 그래서 스프링은 각 Bean을 딱 하나만 만들어 컨테이너에 보관하고, 모든 요청이 그 하나를 공유함. 객체를 하나만 만들어서 재사용하니 메모리와 생성 비용이 크게 절약됨.

---

## 스프링 싱글톤 vs 일반 싱글톤 패턴
둘 다 '객체 하나만' 이라는 결과는 같지만, 방식과 범위가 다름

일반 싱글톤 패턴 - 클래스 안에 private 생성자 + static 인스턴스를 직접 구현
JVM(클래스로더) 단위로 유일 > 한 JVM 안에서 진짜 단 하나

스프링 싱글톤 - 개발자가 코드를 직접 짤 필요가 없음. 스프링 컨테이너가 객체를 하나만 만들어 관리
컨테이너 단위로 유일 > JVM 안이 아닌 컨테이너당 하나

>> 일반 싱글톤은 클래스 자체가 싱글톤을 강제하지만, 스프링 싱글톤은 평범한 객체를 컨테이너가 싱글톤으로 관리할 뿐임

---

## IoC 컨테이너와 싱글톤의 관계
IoC 컨테이너 : Bean을 생성/보관/관리하는 주체.
- IoC(제어의 역전, Inversion of Control) : 객체의 생성/생명주기 관리를 개발자가 아니라 컨테이너가 대신 맡는것
- 스프링은 이 컨테이너가 Bean을 만들 때 기본적으로 싱글톤으로 만들어 내부저장소에 보관

---

## 싱글톤 설계 시 주의점
무상태(Stateless)로 설계해야한다.
> 하나의 객체를 여러 요청(여러 스레드)이 동시에 공유하기 때문에, 객체가 상태를 가지면 동시성 문제가 터짐.

주의점 : 공유 필드에 특정 요청/클라이언트의 데이터를 저장하지 말것. 값은 지역변수, 파라미터, 반환값으로 처리(스레드마다 독립적)할것. 읽기 전용 데이터나 공유 가능한 것만 필드로 생성할것.

---

## IoC/DI가 싱글톤 문제를 어떻게 해결하는가
일반 싱글톤 패턴은 여러 단점이 존재함.
- getInstance()로 직접 호출 > 코드가 특정 클래스에 강하게 결합됨
- private 생성자라 상속/확장이 어려움
- 구체 클래스에 의존 > 테스트 시 가짜 객체(Mock)로 교체 불가 > 테스트 어려움
- 전역 상태라 객체 지향(유연성)을 해침

이때 DI(의존성 주입, **Dependency Injection**)가 이것을 해결

- 객체를 직접 가져오지(getInstance)않고 주입받으니, 구체 클래스에 의존하지 않음 > 인터페이스에 의존 가능
- 테스트할 땐 가짜 구현을 주입하면 됨 > 테스트가 쉬워짐
- 코드에 싱글톤 관련 흔적(private 생성자 등)이 전혀 없음

## 스프링이 싱글톤의 단점을 보완한 방법

| 일반 싱글톤 단점 | 스프링 보완 |
|---|---|
| 코드 오염(private 생성자, static) | 평범한 POJO를 컨테이너가 관리 → 코드 깔끔 |
| 구체 클래스 의존 → 결합도↑ | **DI**로 인터페이스에 의존 가능 |
| 테스트 어려움 | **DI**로 Mock 주입 → 테스트 용이 |
| 상속·확장 어려움 | 일반 객체라 자유로움 |
| 상태 공유 시 동시성 문제 | (이건 보완이 아니라) **무상태 설계로 회피** |
| 항상 하나여야만 함(유연성↓) | **Scope** 지정으로 필요 시 prototype, request 등 선택 가능 |

>>> 웹은 요청이 많아 객체를 매번 만들면 비효율적이라, 스프링은 Bean을 싱글톤으로 관리해 재사용함. 일반 싱글톤 패턴은 코드 오염·테스트 곤란·결합도 증가 같은 단점이 있는데, 스프링은 IoC 컨테이너가 객체 생성·관리를 대신하고 DI로 주입해주어 이 단점들을 없앰. 다만 객체를 공유하므로 동시성 문제를 피하려면 무상태로 설계해야 하고, 싱글톤이 부적합한 경우엔 스코프를 바꿔 대응할 수 있음.

## Bean 이란?
스프링 컨테이너가 만들고 관리하는 객체.
> 특별한 종류의 객체가 아닌, 스프링이 직접 생성/관리하는 자바 객체

```java
@Service          // ← "이 객체를 Bean으로 관리해줘"라고 표시
public class OrderService {
    public void order() { ... }
}
```

내가 `new OrderService()`로 직접 만든 객체는 **Bean이 아닙니다.** (내가 만들고 내가 관리)
`@Service`, `@Controller`, `@Repository`, `@Component` 같은 표시를 붙이거나 `@Bean`으로 등록하면, **스프링이 대신 만들어 관리** → 이게 Bean입니다.

핵심 구분: **누가 만들고 관리하느냐.** 내가 `new`로 만들면 일반 객체, **스프링이 만들어 관리하면 Bean.**

---

## 컨테이너란?
Bean을 만들고, 보관하고, 관리하고, 연결해주는 공간
스프링이 애플리케이션을 시작할 때 만드는 거대한 객체 보관소. 정식 명칭은 ApplicationContext

컨테이너가 하는 일:
- 생성 - @Service 등이 붙은 클래스를 찾아 객체를 만듦
- 보관 - 만든 Bean을 내부 저장소에 담아둠
- 연결(DI) - Bean끼리 필요한 의존관계를 자동으로 주입
- 관리 - Bean의 생성부터 소멸까지 생명주기를 책임짐

## 아는 디자인 패턴 설명 + 적용 예시

**MVC 패턴**
코드를 Model(데이터), View(화면), Controller(요청 처리)로 분리하는 패턴입니다. 세종학당 통합 앱 백엔드에서 Spring MVC 기반으로 API를 설계했는데, Controller에서 요청을 받아 Service로 비즈니스 로직을 위임하고, Repository에서 DB 접근을 분리하는 구조로 작성했습니다. 덕분에 다른 개발자가 인계받아 유지보수할 때 각 레이어의 역할이 명확해서 파악이 쉬웠습니다.

**싱글톤 패턴**
인스턴스를 하나만 생성해서 공유하는 패턴입니다. Spring에서 Bean이 기본적으로 싱글톤으로 관리되는데, DB 커넥션 풀이나 설정 객체처럼 하나만 있어도 되는 자원을 중복 생성하지 않기 위해 사용됩니다.
