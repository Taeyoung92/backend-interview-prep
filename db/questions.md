# 데이터베이스 (DB)

---

## DB 인덱스가 뭔가요?
테이블에서 특정 컬럼을 빠르게 검색하기 위한 자료구조입니다. 책의 목차처럼, 전체를 다 뒤지지 않고 원하는 위치를 바로 찾아갈 수 있게 해줍니다. 내부적으로는 B-Tree 구조로 구성되어 있어 범위 검색에도 효율적입니다. 다만 인덱스는 별도 저장 공간을 쓰고, INSERT·UPDATE·DELETE 시 인덱스도 같이 갱신되기 때문에 쓰기 성능이 떨어질 수 있어서 자주 조회되는 컬럼에만 거는 게 좋습니다.

---

## B-Tree란?
하나의 노드에 여러 개의 키를 담고, 자식을 여러 개 가질 수 있는 균형 트리(Balanced Tree).

우리가 흔히 아는 이진 트리(자식 2개)와 달리, B-Tree의 한 노드는 키를 여러 개 갖고 자식도 여러 개(수백 개까지) 가질 수 있음. 그래서 **납작하고 옆으로 퍼진(낮은 높이)** 형태가 됨

```
             [ 30 | 60 ]              ← 루트 노드 (키 2개, 자식 3개)
         /         |            \
[10 | 20]   [40 | 50]   [70 | 80 | 90]   ← 자식 노드들
```
- 노드 안의 키들은 정렬된 상태로 저장됨
- 키 사이사이의 자식은 그 범위에 해당하는 값을 담음.(예 : 30보다 작으면 왼쪽, 30~60이면 가운데, 60보다 크면 오른쪽)
- 모든 리프 노드가 같은 깊이에 있음

그러므로 검색 요청이 들어온다면 전체 데이터를 다 뒤지지 않고, 각 노드에서 어느 자식으로 갈지만 판단하여 아래로 내려감.

그렇다면 왜 B-Tree인가? 정렬된 배열이나 이진 트리, 해시도 있는데?

**>> 트리 높이가 낮다. 즉, 디스크 접근 횟수가 적다.**
- DB 인덱스는 메모리가 아니라 디스크에 저장됨. 디스크 접근(I/O)은 메모리 접근보다 수만 배 느리므로, 디스크를 몇번 읽느냐가 곧 성능.
- B-Tree는 노드 하나에 키를 수백 개 담으니 자식도 수백 개 > 높이가 3~4단계만 되어도 수백~수억 건을 커버 가능함

**>> 항상 균형이 유지된다(성능이 일정하다)**
- B-Tree는 데이터를 넣고 빼도 노드를 쪼개거나 합치며 자동으로 균형을 맞춤. 그래서 어떤 데이터를 찾든 검색 시간이 일정함

**>> 범위 검색에 강하다(해시 인덱스 대비 우위)**
- 키가 정렬된 상태로 저장되기 때문에 ORDER BY, >, < 같은 범위 및 정렬 쿼리에 강함. (해시 인덱스는 정렬 개념이 없어 범위 검색이 불가능)

**>> 사실은 B+ Tree 이다**
- 대부분의 RDBMS는 정확히 B+ Tree를 씀. B-Tree와의 차이는? > 실제 데이터는 리프 노드에만 저장, 리프 노드끼리 연결 리스트로 이어져있음.

## 복합 인덱스 (A, B, C)에서 where B = ?는 인덱스를 타는가?
타지 않음. 복합 인덱스는 선행 컬럼(A)부터 정렬돼 있어, A 조건 없이 B만으로는 사용할 수 없음.

| 조건 | 인덱스 사용 |
|---|---|
| `WHERE A = ?` | O |
| `WHERE A = ? AND B = ?` | O |
| `WHERE B = ?` | X (A를 건너뜀) |
| `WHERE A = ? AND C = ?` | A까지만 활용, C는 부분적 |

## 인덱스를 걸었는데 안 타는 경우
- 인덱스 컬럼에 함수/연산 적용 : `WHERE YEAR(date) = 2024`, `WHERE salary * 12 > ...`
- 앞부분 와일드카드 : `LIKE '%abc'` (`'abc%'`는 탐)
- 타입 불일치(암묵적 형변환) : 문자 컬럼에 숫자로 조회
- 복합 인덱스에서 선행 컬럼 누락
- 조회 결과가 테이블의 너무 많은 비율일 때 → 옵티마이저가 풀스캔이 낫다고 판단
