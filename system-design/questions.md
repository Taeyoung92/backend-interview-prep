# 시스템/기능 설계 문제

## 알림 시스템

### 알림을 구현할 때 어떤 구현 방법이 있는지
방법 3가지 - Polling / SSE / WebSocket

**1. 폴링**
- 장점 : 구현이 가장 단순. 특별한 인프라 불필요. HTTP 그대로 사용
- 단점 : 새 알림이 없어도 계속 요청 → 트래픽/서버 부하 낭비. 주기 사이의 지연 발생
- 적합 : 실시간성이 별로 중요하지 않고, 트래픽이 적은 간단한 서비스

**2. SSE**
- 장점 : 알림에 가장 적합한 구조(알림은 서버가 일방적으로 주는 단방향이므로). 웹소켓보다 가볍고 구현이 간단함. HTTP 기반이라 자동 재연결 등 지원
- 단점 : 단방향이라 클라이언트가 서버로 보낼 길은 없음. 브라우저당 연결 수 제한, 일부 구형 환경 지원 이슈
- 적합 : 실시간 알림, 피드 업데이트처럼 받기만 하면 되는 경우

**3. 웹소켓**
- 장점 : 실시간성 최고, 양방향이라 알림 + 채팅 등 복합 기능에 유리
- 단점 : 양방향 연결 유지에 서버 자원 부담이 큼. 구현·운영 복잡도 높음 (알림만 필요하면 과한 선택)
- 적합 : 채팅처럼 양방향이 함께 필요하거나, 매우 높은 실시간성이 요구될 때

**고려해야 할 포인트**
1. 알림 저장(영속성) - 사용자가 접속 중이 아닐 때 온 알림은? → DB에 저장해두고, 접속하면 보여주기. 실시간 전송과 별개로 저장은 필수.
2. 읽음 처리 - 읽음/안읽음 상태 관리, 안읽은 개수 표시(배지).
3. 다중 서버 환경 - 서버가 여러 대면, 알림 대상 사용자가 어느 서버에 연결돼 있는지 모름 → Redis Pub/Sub이나 메시지 큐(Kafka)로 서버 간에 알림을 전파.
4. 연결 관리 - SSE/웹소켓은 연결이 끊길 수 있음 → 재연결 처리, 끊긴 연결 정리(좀비 커넥션 방지)
5. 비동기 처리 - 알림 전송이 본 로직(예 : 주문 처리)을 막으면 안 됨 → 비동기/이벤트 기반으로 분리. 스프링이면 @Async나 이벤트 발행(ApplicationEventPublisher).
6. 장애 대응 - 알림 전송 실패 시 재시도, 푸시 서비스 장애 시 처리.

### 알림 시스템이 메시지 브로커를 어떻게 활용 가능할까?
단순 알림이라면 브로커 없이 생성 가능하나, 다음 상황과 같다면 브로커가 필요해 짐

브로커가 필요한 상황:
1. 알림을 받을 서비스/대상이 여러 곳(앱 푸시 + 이메일 + SMS 동시발동 등)
2. 서버가 여러 대 → 알림 대상이 어느 서버에 붙어 있는지 모름
3. 주문 처리가 알림 전송을 기다리느라 느려지면 안 됨(비동기 분리)
4. 알림이 폭증(전체 공지)해도 시스템이 버텨야 함

보통의 알림 시스템 구조:
```
주문서비스 ─발행─→ 메시지 브로커 ─→ 알림 컨슈머 ──→ 채널별 발송 ──→ 사용자
(이벤트 발생)    (Kafka/Redis)    (구독·처리)      ├ SSE/WebSocket
                                       ↓             ├ FCM/APNs (앱 푸시)
                                  알림 DB 저장        ├ 이메일
                                (안 읽은 알림 보관)   └ SMS
```

구현 시 고려 사항:
1. 실시간 전송과 저장을 분리 - 실시간으로 밀어주는 것(SSE)과, 미접속자를 위해 DB에 쌓아두는 것은 별개로 둘 다 해야하며 접속하면 안 읽은 알림을 DB에서 불러옴.
2. 어떤 브로커를 쓸지
   - Redis Pub/Sub : 실시간 broadcast용, 빠르지만 유실 가능(그 순간 구독자가 없다면 사라짐) → 실시간 전달 채널에 적합
   - Kafka : 유실되면 안 되는 알림, 대용량, 재처리 필요 시. 디스크에 보관
   - 실무에선 둘을 조합할 때도 있음(Kafka로 안정적 처리 + Redis로 실시간 push)
3. 멱등성(중복 방지) - 브로커는 보통 최소 한번 전달이라 같은 알림이 두 번 올 수 있음. → 알림 ID로 중복 체크해 한 번만 발송.
4. 실패/재시도 - 푸시/이메일 발송 실패 시 재시도, 계속 실패하면 별도 보관(Dead Letter Queue)
5. 부하/폭증 대응 - 전체 공지처럼 한 번에 수만 건 → 브로커가 완충, 컨슈머가 감당 가능한 속도로 처리. 컨슈머를 여러 개 두어 분산 처리.
6. 알림 설정/우선순위 - 사용자가 끈 알림은 안 보냄, 중요 알림(결제) 우선 처리 등.

## 메시지 브로커(Message Broker)란?
보내는 쪽과 받는 쪽 사이에서 메시지를 중개/전달해주는 시스템(중간 서버)
퍼블리셔가 브로커에게 던지고, 메시지 브로커는 구독자에게 전달. 대표적으로 Kafka, RabbitMQ, Redis(Pub/Sub), ActiveMQ등이 있음.

메시지 브로커의 사용 이유?
1. 결합도를 낮춤 - 보내는 쪽과 받는 쪽이 서로를 직접 몰라도 됨. 새 구독자(통계 서비스 등)를 추가해도 기존 코드를 안 고쳐도 됨.
2. 비동기 처리 - 주문서비스는 브로커에 던지고 바로 자기 일 끝냄. 알림 전송을 기다리지 않음 → 응답 속도↑ (앞서 알림에서 다룬 "본 로직을 막지 않는 비동기 처리"가 이것)
3. 장애 격리 + 안정성 - 알림서비스가 잠깐 죽어도 주문서비스는 멀쩡함. 브로커가 메시지를 들고 있다가 살아나면 전달. (메시지 유실 방지)
4. 부하 분산/완충(버퍼) - 트래픽이 폭증해도 브로커가 메시지를 쌓아두고, 받는 쪽이 처리 가능한 속도로 가져감 → 받는 쪽이 터지지 않음.

## 메시지 큐와 Pub/Sub의 차이점은?
두 개 다 메시지를 전달하는 모델이지만,

- 메시지 큐 - 메시지가 큐에 쌓이고, 여러 소비자 중 한 명만 가져가 처리. 가져가면 큐에서 사라짐
- Pub/Sub - 메시지가 주제에 발행되고, 구독자 전원이 똑같이 받음.

---

## 메시지가 중복 전달되면? (멱등성)
대부분의 브로커는 at-least-once(최소 한 번)라 같은 메시지가 두 번 올 수 있음. 멱등성으로 처리 → 같은 작업을 여러 번 해도 결과가 같게 만드는 것.
- 메시지마다 고유 ID 부여 → 처리한 ID를 기록 → 이미 처리한 ID면 무시

---

## 알림 순서를 보장하려면? (Kafka 파티션)
Kafka는 파티션 단위로만 순서를 보장함. 같은 사용자의 알림이 순서대로 와야 한다면, 사용자 ID를 파티션 키로 지정 → 같은 사용자 메시지는 항상 같은 파티션으로 → 순서 유지.

> 주의 : 파티션이 여러 개면 파티션 간 순서는 보장되지 않아, 순서가 중요한 단위를 키로 묶는 것이 핵심.
